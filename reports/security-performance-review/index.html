Security and performance review

Zypheron CLI lab run against Juice Shop and Metasploitable

Review date: July 8, 2026. Targets were local Docker containers bound to 127.0.0.1. The intentionally vulnerable target findings are separated from Zypheron product findings.

The highest-impact product issue found is scan startup latency and hangs caused by unbounded version probes in the Kali tool manager. With a normal PATH, msfconsole --version blocked long enough that tools check exceeded 45 seconds and selected scan commands had to be interrupted. With a controlled PATH, the same Zypheron scans completed and produced usable results.

Zypheron Product Findings

High

Unbounded tool version probes can hang scans and tool checks

Evidence: zypheron-go/internal/kali/tools.go:60 calls getToolVersion for every installed tool, and tools.go:337 uses exec.Command(...).Output() without a context deadline. In this lab, msfconsole --version blocked and made normal PATH scans unusable until the PATH was isolated.

Fix: replace the Kali manager probe with exec.CommandContext and a 1-2 second timeout, reuse the timeout pattern already present in zypheron-go/internal/tools/checker.go:479, cache versions, and avoid probing unrelated tools before a selected-tool scan.

Medium

Autopent command exists but is not registered

Evidence: zypheron-go/internal/commands/autopent.go:16 defines AutoPentCmd(), but zypheron-go/cmd/zypheron/main.go:156 through main.go:185 registers many commands without adding commands.AutoPentCmd(). The built CLI returns unknown command "autopent".

Fix: register the command in main.go, add a root command test that asserts autopent is present, and verify license gating still runs before execution.

Medium

AI engine health reports started, then breaks the request pipe

Evidence: zypheron ai status printed that the AI engine started and was running, then returned failed to get health status: failed to send stdio request: write |1: broken pipe. No Python server process remained afterward.

Fix: make startup wait for a real health response, surface Python startup stderr in the status error, and only print running status after a completed health check.

Medium

API token counting depends on runtime network access

Evidence: zypheron-api/app/services/token_tracking.py:91 calls tiktoken.get_encoding. In the test environment, the first GPT-4 count attempted to fetch cl100k_base.tiktoken from OpenAI public blob storage and failed DNS resolution.

Fix: prewarm or vendor the tiktoken cache for supported encodings, make tests use an offline fixture, and degrade to a conservative estimate if the encoding cannot be loaded at runtime.

Low

JSON scan mode still performs global environment work before execution

Evidence: selected-tool scans in JSON mode still paid the full tool detection cost before executing the requested tool. This makes automation slower and turns unrelated tool issues into selected-scan failures.

Fix: for scan --tool X --format json --no-input, check only the selected executable and return machine-readable errors without global version inventory.

Recommended Fix Order

Priority Fix Validation
1 Add timeouts and selected-tool fast path to Kali tool detection. zypheron tools check completes under 5 seconds with Metasploit installed; JSON scan starts without probing unrelated tools.
2 Register AutoPentCmd() in the root command and add command registration coverage. zypheron autopent --help works and license/safety prompts still trigger.
3 Fix AI engine startup and status health checks. zypheron ai status returns a single truthful status and includes startup errors when health fails.
4 Make token counting offline-safe. API token tracking tests pass without network access or pre-existing user cache.
5 Improve partial scan result semantics. Timed-out scans report both timeout status and captured findings in a clear JSON shape.
